# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A SwiftUI voice journal that transcribes spoken entries on-device with Apple's own
`SFSpeechRecognizer` and derives mood/topics from the transcript. The original visual
prototype's behavior was a browser mock (fake transcription, hardcoded mood) and has been
replaced end-to-end with real functionality. See "Deviations from Yap.dc.html" below.

Transcription previously ran through a bundled Whisper CoreML model (via
[WhisperKit](https://github.com/argmaxinc/argmax-oss-swift)) as a second, more-accurate pass
after Stop. That's gone: the bundled model was a genuine liability (594MB→144MB across two
revisions, and the larger one crashed a real iPhone 12 into a full reboot from memory
pressure — see the "Deviations" section below), and Apple's own on-device recognizer is
already quite good, ships with the OS for free, and needs zero load time. The whole app is
~4.5MB now instead of 750MB+.

## Build and test

`Yap.xcodeproj` and `Yap/Info.plist` are **generated by XcodeGen and gitignored** — never
hand-edit them. Change `project.yml` instead, and re-run `xcodegen generate` after adding,
moving or deleting any source file.

```sh
cd ~/Documents/Yap
xcodegen generate
export DEVELOPER_DIR=/Applications/Xcode.app/Contents/Developer

xcodebuild -project Yap.xcodeproj -scheme Yap \
  -destination 'generic/platform=iOS Simulator' build

# Install + launch on a booted simulator
SIM=<simulator-udid>
xcodebuild -project Yap.xcodeproj -scheme Yap -destination "id=$SIM" build
xcrun simctl install $SIM <DerivedData>/Build/Products/Debug-iphonesimulator/Yap.app
xcrun simctl launch $SIM com.timothykoelsch.Yap
```

For device installation, open the generated project in Xcode and select your own team in
Signing & Capabilities. Never commit a personal development-team identifier.

Screenshotting states with no cold-launch path — DEBUG-only launch arguments read in
`Store.applyLaunchOverrides`:

```sh
xcrun simctl launch $SIM com.timothykoelsch.Yap -dark
xcrun simctl launch $SIM com.timothykoelsch.Yap -segment insights
xcrun simctl launch $SIM com.timothykoelsch.Yap -openRecording
xcrun simctl io $SIM screenshot out.png
```

Live mic + transcription can't be scripted headlessly in the simulator (no fake audio
input); test that on a real device, or manually with the simulator's host-mic passthrough.

## Architecture

**`Store`** (`Yap/Store.swift`) is the single `@MainActor ObservableObject` — active
section, entries, recording phase/timer, and detail-navigation state. It owns every mutation and is
injected via `.environmentObject`, mirroring the design's single `DCLogic` class.

**`Transcriber`** (`Yap/Speech/Transcriber.swift`) runs **one engine for both jobs**: Apple's
on-device `SFSpeechRecognizer` (`requiresOnDeviceRecognition = true`, locale `en-US`) drives
both the live captions while recording *and* the saved transcript. There used to be a second
engine (bundled Whisper via WhisperKit) for a more-accurate save pass — removed entirely, see
"Deviations" below for why.

- **Live captions** are the recognizer's incremental partial results
  (`shouldReportPartialResults = true`), free/offline/no-API-key, appearing within the same
  frame they're recognized. Requires `NSSpeechRecognitionUsageDescription` (alongside the mic
  string in `project.yml`) and a separate authorization prompt (`SpeechPermission.swift`),
  requested on first tap of the record button. Unlike the mic permission, denial here is
  fatal to recording — there's no fallback engine anymore, so `Transcriber.startRecording()`
  returns `.failure(.speechPermissionDenied)` and `Store` surfaces a clear alert rather than
  silently producing empty entries.
- **The saved transcript** is the *same* recognizer's `isFinal` result: `stopAndTranscribeFinal()`
  calls `endAudio()` and waits up to ~900ms for that final result (which resolves any
  misheard words using the whole utterance's context, so it's usually a touch cleaner than
  the last live partial) before falling back to whatever the last partial was, so Stop is
  never held up waiting on something that might not arrive. No separate decode pass, no
  multi-second wait — the entry is ready within about a second of tapping Stop.
- `AVAudioEngine` + one `inputNode.installTap` feeds the mic buffers to
  `SFSpeechAudioBufferRecognitionRequest.append(_:)` directly (native format) for
  recognition, and separately resamples each buffer to 16kHz mono via `AVAudioConverter`
  (this project's own conversion, not a third-party utility) into a lock-guarded
  `AudioSampleAccumulator` — plain, not `@MainActor`, since the tap callback runs on a
  real-time audio thread and can't hop to the main actor per-buffer (~every 30-60ms) without
  adding needless overhead. Those accumulated raw samples are what `EntryAudioStore` persists
  as the entry's `.m4a` + waveform — entirely independent of the transcription engine.
- Waveform bars are driven by peak amplitude on those same captured buffers
  (`AudioSampleAccumulator.latestPeak`), polled onto `@Published levels` by a 10Hz timer —
  real mic input, not a canned CSS loop.
- The recognition task auto-restarts on non-silence errors or a natural `isFinal` timeout
  mid-recording (Apple's on-device recognizer has its own internal time limit), layering new
  text onto `confirmedTextPrefix` rather than replacing `liveText` outright — otherwise a
  pause-triggered restart would visibly wipe everything said so far.
- **Views must observe `Transcriber` directly** (`@ObservedObject`), not read it off
  `store.transcriber` from a view that only holds `@EnvironmentObject var store: Store` —
  `Store` does not forward `Transcriber`'s `objectWillChange`, so a view doing that only
  redraws when some unrelated `Store` `@Published` property happens to change (e.g.
  `recordingPhase` flipping at Stop), which looks exactly like "text only appears at the
  end" even once the data wiring is correct. `RecordingView` takes `transcriber` as an
  explicit `@ObservedObject` parameter from `RootView` for this reason — keep it that way.
- **Live transcript styling** (`RecordingView`): recognized words use ordinary journal
  typography and color. System-shaped dictation feedback keeps attention on the words and
  avoids flicker when the recognizer revises a partial result. Reduce Motion also disables
  the recording pulse and word-entry animation.

**`JournalSimplifier`** (`Yap/AI/JournalSimplifier.swift`) is the one deliberate exception to
the app's otherwise on-device design. `DetailView`'s "Clean up" action first explains that
the selected entry is sent to NVIDIA's hosted inference API (NIM, OpenAI-compatible chat
completions) to strip verbal filler — "um," "uh," false starts, mid-sentence repeats —
without rephrasing, summarizing, or changing word choice. The result is shown beside the
original and saved only after the user explicitly chooses it. Nothing else in the app makes
a network call. The real key is supplied locally in `Yap/AI/Secrets.swift`, created from
`Yap/AI/Secrets.swift.example`; it is gitignored and must never be committed. A client-
embedded key is extractable from a compiled app, so distributed apps should use a server-
side proxy instead.

**`RootView`** (`Yap/Screens/RootView.swift`) uses a native `NavigationStack` for entry
detail, with `Store.detailEntry` driving its destination binding so the system back button
and interactive back gesture stay in sync. The full-screen `RecordingView` remains mounted
above the stack in a `ZStack`, gated by `.allowsHitTesting`, so it can cover either the
journal or an entry while recording continues.

**Persistence** is a flat `entries.json` in the app's Documents directory (`Model.swift`,
`EntryStore`) — no CoreData/SwiftData, the data shape doesn't need it. A real first launch
starts with zero entries (see `Store.init()`) — the design's 12 seed entries auto-wrote on
every fresh install until a new-user audit flagged it: every real install opened straight
into what looked like someone else's private journal (a fabricated 10-day streak, mood
trend copy about people/days that never happened), which is a bad first impression for an
app whose whole pitch is on-device privacy. `EntryStore.seedEntries()` is now reachable
only via the DEBUG-only `-seedDemo` launch argument, for screenshots/demos — see
`Store.applyLaunchOverrides`.

## Visual system

See `README.md` and `DESIGN_AUDIT.md` for the current design direction and full review.
The journal uses a paper-and-ink palette, text-first entries, a pinned recording action,
native segmented navigation, native entry-detail navigation with the system back gesture,
estimated mood labels, and system appearance / accessibility settings. Glass is reserved
for small native controls. The old floating action button and custom segmented control have
been removed. The deployment target is iOS 26.0.

## Deviations from Yap.dc.html

The `.dc.html`'s `Component` class is a browser mock. Every mocked behavior below is real
in this app:

- **Transcription**: the design replays a hardcoded sentence word-by-word on a `setTimeout`
  loop. This app records real audio and produces genuinely instant live captions *and* a
  saved transcript from the same source — Apple's on-device `SFSpeechRecognizer`. 100%
  on-device, no network call ever, no API key, no per-use cost.

  This went through two bundled-Whisper-model revisions before landing here, both removed:
  first `distil-whisper_distil-large-v3` (594MB) — despite the "distil" name, only its
  decoder was distilled, so its encoder was the full 32-layer large-v3 encoder (339MB
  alone), and loading/ANE-compiling it crashed a real iPhone 12 (4GB RAM) into a full device
  reboot on first launch, not just an app crash. Then `openai_whisper-base.en` (144MB),
  which loaded safely but still cost a multi-second wait after Stop and ~150MB of app
  storage for accuracy gains that turned out to be marginal over Apple's own recognizer.
  WhisperKit and the bundled model are gone entirely now — the app is ~4.5MB. If bundling
  any model again, verify it on the actual lowest-RAM target device first (ideally on a
  charger) — a bad load here takes down the whole phone, not just the app, so this isn't
  safe to find out from a crash report after shipping.
- **Mood**: the design hardcodes `mood: 0.6` on every new entry. This app scores the real
  transcript with Apple's on-device `NLTagger` sentiment analysis (`Store.sentiment(of:)`),
  mapped directly to the design's -1...1 scale.
- **Topics**: the design hardcodes `topics: ['Work']`. This app runs the transcript through
  a small on-device keyword classifier (`TopicClassifier` in `Model.swift`) against the
  design's topic vocabulary (Work, Deadlines, Friends, Relationships, Sleep, Money), falling
  back to "General" if nothing matches.
- **Patterns**: the design hardcodes three fixed sentences. This app generates deterministic,
  on-device pattern copy from topic/mood aggregates (`Store.insightCards`), clearly labeled
  as estimates and withheld until at least five entries exist. It is not generative AI.
- **Waveform bars**: the design animates 3 bars per side on a fixed CSS keyframe loop. This
  app drives bar height from real mic input peak amplitude (`AudioSampleAccumulator.latestPeak`
  on the live-captured buffers).
- Accent stays a single restrained blue (`#3F6687`); the design's per-user color picker prop
  was dropped, matching this user's established preference for one blue accent rather than a
  palette.
